# Client Trust AI Automation LinkedIn Swipe

## Purpose

Use this reference when creating LinkedIn content that makes potential clients
understand three things:

1. Stanley builds practical AI automation systems.
2. The work is process-driven, not random AI hype.
3. Clients should trust Stanley because he can explain the business problem,
   the automation workflow, the tools, the implementation path, and the outcome.

This is a pattern library, not a copy bank. Do not copy the source posts. Study
their structure, then create original Stanley content from his own workflows,
client use cases, builds, tools, and proof.

## Stanley B2B Positioning Rule

Every LinkedIn or X post for the automation services lane should be written for
a real buyer, not a general AI audience.

Before drafting, choose:

1. Target audience: industry, company type, or department.
2. Business function: marketing, UGC production, paid ads, sales, operations,
   reporting, research, onboarding, customer support, or another repeatable
   company workflow.
3. Bottleneck: what currently takes too long, costs too much, needs too many
   manual steps, or blocks scale.
4. Automation angle: what Stanley and his team can automate.
5. Proof or mechanism: a real build, architecture, workflow, tool chain,
   before/after, or implementation detail.
6. Business outcome: time saved, faster content output, more campaign velocity,
   cleaner handoff, reduced manual work, better consistency, or a clearer path
   to scale.
7. CTA: invite founders, operators, agencies, or teams to discuss the bottleneck,
   request a workflow audit, or book a call.

Default target geography: clients and companies in the USA, UK, Canada, and
similar foreign markets.

## Stanley Proof Points To Reuse

Use these as owned proof points when relevant:

- Claude content creation agentic system: reduced a client's app-promotion UGC
  production workflow from about one week to a few hours. The old process
  required manual recording and editing. The new system handles the production
  pipeline end to end and produces ready-to-post content.
- n8n Google Ads automation: automates Google Ads campaign work.
- More proof points should be added only when Stanley provides the details.

Do not overclaim. If a detail is not provided, frame it as the workflow,
mechanism, or direction, not as a fake metric.

## Common Winning Structure

Most examples use this arc:

1. Sharp hook.
2. Pain or misconception.
3. Specific AI automation mechanism.
4. Step-by-step process.
5. Proof, numbers, or concrete output.
6. Business interpretation.
7. CTA.

For Stanley, the best version is:

```text
Manual process clients recognize
-> why the current approach is expensive or slow
-> how Stanley automates it
-> what tools or architecture are involved
-> proof/output/checkpoint
-> what this means for the business
-> CTA to DM/comment/book a workflow audit
```

The post should feel like it is speaking to a company problem. Good angles:

- For app companies: automate UGC ad/video production so marketing teams can
  test more creatives faster.
- For agencies: automate content and ad operations so client delivery is less
  manual.
- For SaaS teams: automate reporting, content repurposing, onboarding assets,
  or customer-support workflows.
- For e-commerce brands: automate ad creative production, campaign setup,
  product-content generation, or weekly performance reporting.
- For service businesses: automate lead research, proposal drafting, follow-up,
  client onboarding, and handoff documents.

## Archetypes To Recreate

### 1. The One-Line Fix

Source pattern:
A creator shows that people are doing too much manual prompting and should move
the repeated instructions into a reusable system.

Stanley version:

```text
Stop writing new prompts for the same business task every week.

Build a reusable AI workflow once.

Example:
- lead research
- report generation
- follow-up drafting
- content repurposing
- client onboarding

The prompt is not the asset.
The process is.
```

Use when:

- Explaining custom GPTs, Claude Skills, agents, SOPs, or internal automations.
- Showing that AI automation is about reusable operating systems.

Trust signal:
Stanley understands system design, not just prompting.

### 2. The Rebuilt System Teardown

Source pattern:
A creator finds a working online business/content system, rebuilds the workflow,
then lists each automation step.

Stanley version:

```text
I took a manual workflow and rebuilt it as an AI automation system.

Before:
Every task was done by hand.

After:
One command runs the workflow.

The system:
1. Collects the source material.
2. Extracts the useful data.
3. Generates the output.
4. Checks quality.
5. Saves the handoff files.
6. Stops for approval.
```

Use when:

- Showing a content engine, lead engine, report generator, job automation,
  video workflow, or research system.

Trust signal:
Stanley can reverse-engineer a workflow and turn it into a repeatable asset.

### 3. The Full Stack Inventory

Source pattern:
A creator lists plugins, skills, MCPs, and tools to show the real system behind
their output.

Stanley version:

```text
The AI stack behind my automation work:

1. Research layer
2. Browser layer
3. Data layer
4. Drafting layer
5. QA layer
6. Image/video layer
7. Approval layer
8. Publishing layer

The tool names matter less than the chain.
One tool writes.
The system delivers.
```

Use when:

- Showing behind-the-scenes infrastructure.
- Teaching clients why a proper AI setup is more than ChatGPT.

Trust signal:
Stanley can architect connected workflows across multiple tools.

### 4. The Contrarian CEO/Client Warning

Source pattern:
The post starts by attacking a common executive mistake, then presents a more
practical service model.

Stanley version:

```text
Hiring one "AI person" will not fix your business.

Your bottleneck is not AI knowledge.
It is undocumented manual process.

Before you hire:
- map the repeated tasks
- find the bottlenecks
- decide what should stay human
- automate one workflow at a time
- measure the saved time

That is how AI becomes useful.
```

Use when:

- Selling audits, implementation retainers, internal automation support, and
  workflow mapping.

Trust signal:
Stanley gives strategic advice instead of promising magic.

### 5. The Natural-Language Automation Demo

Source pattern:
The creator shows that a previously technical task can now be done by telling AI
what to do in plain language.

Stanley version:

```text
You should not need to click through 14 tools to get one task done.

Tell the system:
"Find the leads."
"Write the report."
"Generate the captions."
"Cut the silences."
"Prepare the client handoff."

Then let the workflow run.

That is the real promise of AI automation:
less operating the tool,
more directing the outcome.
```

Use when:

- Demonstrating automations that connect Claude/ChatGPT to browsers, files,
  spreadsheets, video tools, CRMs, or ad platforms.

Trust signal:
Stanley makes AI understandable for business owners.

### 6. The Client Expectation Reality Check

Source pattern:
The creator explains that clients often want senior-level outcomes for intern
budget and no guidance.

Stanley version:

```text
AI will not save a broken process.

If your inputs are vague,
your files are scattered,
your team has no SOP,
and nobody knows what "done" means,
AI will only make the mess faster.

Good automation needs:
- clear inputs
- clear rules
- clear ownership
- clear QA
- clear approval

That is what we build first.
```

Use when:

- Qualifying clients.
- Teaching why setup, documentation, and process design matter.

Trust signal:
Stanley is honest about what AI can and cannot do.

### 7. The Wow-Moment Case Study

Source pattern:
A creator shares a specific surprise: Claude/AI performed a practical task by
using existing tools and writing the instructions.

Stanley version:

```text
I gave AI the outcome, not the steps.

It inspected the files.
Picked the tool.
Wrote the command.
Ran the workflow.
Checked the output.
Saved the result.

This is why AI automation is different from normal software:
you can build around outcomes, not buttons.
```

Use when:

- Sharing local builds, internal experiments, or client-safe demos.

Trust signal:
Stanley has hands-on proof and understands the implementation layer.

## Visual Patterns To Recreate

Use these visual directions for Penpot or local renderers:

1. Big contrarian headline.
   - Example style: one large sentence, one highlighted word, minimal background.
2. Stack map.
   - Three columns: Tools, workflows, outcomes.
3. Before/after process.
   - Left side manual workflow, right side automated workflow.
4. Workflow teardown.
   - Numbered steps, arrows, checkpoints.
5. Client reality check.
   - Quote card or checklist with "what clients think" vs "what they need".
6. Command-to-output diagram.
   - Prompt/command at top, output package at bottom.
7. Proof board.
   - Time saved, file created, system generated, approval required.

Always keep the image text source-derived or Stanley-workflow-derived. Avoid
random motivational quotes.

## Stanley Voice Rules

Use:

- practical
- direct
- process-first
- plain English
- specific workflows
- clear client stakes
- real constraints
- proof or artifact paths when available

Avoid:

## Scraping And Recreation Workflow

When the user provides reference links:

1. Open each source.
2. If public text is available, extract:
   - creator
   - topic
   - hook pattern
   - pain point
   - automation mechanism
   - proof
   - CTA
   - visual type
3. If source text is blocked, ask for pasted text or screenshots.
4. Save a source summary, not a full copied post.
5. Build a "recreation angle" for Stanley.
6. Draft original posts from Stanley's services, workflows, or demos.
7. Create editable visual assets in the normal content package.
8. If Penpot is running, auto-import editable SVGs into Penpot, not just save
   them on disk.
9. Generate the platform images from the editable source files before calling
   the package complete.

## Client-Trust Content Formula

Use this formula for original posts:

```text
Hook:
Name the mistake, bottleneck, or surprising automation.

Context:
Show the manual process clients already recognize.

Mechanism:
Explain the automation architecture in simple terms.

Proof:
Show artifact, time saved, steps automated, or system output.

Trust lesson:
Explain what the client should understand.

CTA:
Invite them to comment, DM, or ask for an automation audit.
```

## Safe Rewriting Rule

Do not write:

```text
I found [their exact example] and rebuilt it...
```

Unless Stanley actually did that work.

Instead write:

```text
This is the kind of workflow businesses should be building:
...
```

or:

```text
We use the same principle for client operations:
...
```
